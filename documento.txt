# 1. Análisis del Dominio y Requerimientos Informacionales

## 1.1 Descripción del dominio de aplicación

### Contexto organizacional o de negocio

El presente proyecto plantea el diseño de una base de datos para un **Sistema de Gestión de Restaurante**, cuyo objetivo es organizar y administrar la información relacionada con las principales operaciones de un establecimiento dedicado a la atención de clientes y venta de alimentos y bebidas.

El sistema permitirá gestionar información de los clientes, empleados, mesas, reservas, categorías, productos, pedidos, detalles de pedidos y pagos. De esta manera, se busca centralizar la información y facilitar su registro, consulta y actualización.

Las operaciones principales del restaurante comprenden el registro de clientes, administración de mesas, gestión de reservas, administración de productos y categorías, registro de pedidos, seguimiento de los productos solicitados y registro de los pagos correspondientes.

El sistema considera la participación de diferentes usuarios, entre ellos administradores, recepcionistas, mozos, cajeros, cocineros y clientes, cada uno con diferentes necesidades de información dentro del proceso de atención.

### Problemática informacional identificada

En un restaurante que no cuenta con una adecuada estructura de información pueden presentarse problemas como la duplicidad de datos, dificultad para conocer la disponibilidad de las mesas, registros desorganizados de pedidos y dificultad para consultar el historial de ventas y pagos.

Asimismo, mantener la información de productos y categorías de manera repetitiva puede generar inconsistencias. Por ejemplo, si la información de una categoría se registra directamente en diferentes pedidos, una modificación podría requerir actualizar múltiples registros.

Otro problema es la dificultad para mantener un historial organizado de las reservas, pedidos y pagos realizados por los clientes.

Por ello, se plantea una base de datos estructurada que permita organizar la información mediante entidades relacionadas, reduciendo la redundancia y facilitando la integridad y consistencia de los datos.

### Reglas de negocio identificadas y cómo se implementaron

| Código | Regla de negocio |
|---|---|
| RN-01 | Cada cliente debe estar identificado de manera única dentro del sistema. |
| RN-02 | Cada mesa debe tener un número único. |
| RN-03 | Una reserva debe estar asociada a un cliente y a una mesa. |
| RN-04 | Un cliente puede realizar varias reservas en diferentes momentos. |
| RN-05 | Una mesa puede encontrarse disponible, reservada u ocupada. |
| RN-06 | Un pedido debe estar asociado a un cliente. |
| RN-07 | Un pedido debe ser registrado por un empleado. |
| RN-08 | Un pedido puede contener uno o varios productos. |
| RN-09 | Un producto puede formar parte de diferentes pedidos. |
| RN-10 | Cada producto pertenece a una categoría. |
| RN-11 | Cada detalle de pedido debe registrar la cantidad solicitada y el precio unitario correspondiente. |
| RN-12 | Un pedido puede generar un pago asociado. |
| RN-13 | Los empleados pueden desempeñar diferentes funciones dentro del restaurante. |
| RN-14 | La información de productos y categorías debe mantenerse separada para evitar la duplicidad de información. |

Estas reglas se implementan mediante las entidades, atributos, claves y relaciones definidas posteriormente en el modelo conceptual y en el modelo relacional.

# 2. Modelo Conceptual: Diagrama Entidad-Relación

## 2.1 Identificación de entidades

### Entidades principales del dominio

Para representar el funcionamiento del Sistema de Gestión de Restaurante se identificaron las siguientes entidades:

- **CLIENTE**
- **EMPLEADO**
- **MESA**
- **RESERVA**
- **CATEGORIA**
- **PRODUCTO**
- **PEDIDO**
- **DETALLE_PEDIDO**
- **PAGO**

### Justificación de cada entidad identificada

| Entidad | Justificación |
|---|---|
| CLIENTE | Permite almacenar la información de las personas que realizan reservas y pedidos. |
| EMPLEADO | Representa al personal encargado de participar en las operaciones del restaurante. |
| MESA | Representa los espacios físicos disponibles para la atención de los clientes. |
| RESERVA | Permite registrar las solicitudes de reserva realizadas por los clientes. |
| CATEGORIA | Permite clasificar los productos ofrecidos por el restaurante. |
| PRODUCTO | Representa los alimentos y bebidas disponibles para los clientes. |
| PEDIDO | Representa una solicitud de productos realizada por un cliente. |
| DETALLE_PEDIDO | Permite registrar los productos incluidos en cada pedido, junto con sus cantidades y precios. |
| PAGO | Permite registrar la información del pago asociado a un pedido. |

## 2.3 Relaciones entre entidades

### Descripción de relaciones identificadas

| Relación | Cardinalidad | Descripción |
|---|---|---|
| CLIENTE — RESERVA | 1:N | Un cliente puede realizar varias reservas. |
| RESERVA — MESA | N:1 | Una reserva corresponde a una mesa. |
| CLIENTE — PEDIDO | 1:N | Un cliente puede realizar varios pedidos. |
| EMPLEADO — PEDIDO | 1:N | Un empleado puede registrar varios pedidos. |
| PEDIDO — DETALLE_PEDIDO | 1:N | Un pedido puede contener varios detalles. |
| PRODUCTO — DETALLE_PEDIDO | 1:N | Un producto puede aparecer en diferentes detalles de pedido. |
| CATEGORIA — PRODUCTO | 1:N | Una categoría puede contener varios productos. |
| PEDIDO — PAGO | 1:1 | Un pedido tiene asociado un pago. |

La relación conceptual entre **PEDIDO** y **PRODUCTO** es de tipo **N:M**, ya que un pedido puede contener varios productos y un producto puede formar parte de diferentes pedidos. Esta relación se resuelve mediante la entidad asociativa **DETALLE_PEDIDO**.

### Grado de las relaciones

Todas las relaciones identificadas en el modelo son de **grado binario**, debido a que cada relación involucra a dos entidades.

### Cardinalidades

Las cardinalidades utilizadas son:

- **1:1** para PEDIDO — PAGO.
- **1:N** para CLIENTE — RESERVA.
- **1:N** para CLIENTE — PEDIDO.
- **1:N** para EMPLEADO — PEDIDO.
- **1:N** para CATEGORIA — PRODUCTO.
- **1:N** para PEDIDO — DETALLE_PEDIDO.
- **1:N** para PRODUCTO — DETALLE_PEDIDO.
- **N:1** para RESERVA — MESA.

### Roles en las relaciones

Los principales roles identificados son:

- **CLIENTE:** realiza reservas y solicita pedidos.
- **EMPLEADO:** registra y atiende pedidos según su función.
- **MESA:** representa el espacio físico asignado a una reserva.
- **PEDIDO:** representa la operación que contiene los productos solicitados.
- **PRODUCTO:** representa los elementos que pueden ser incluidos en un pedido.

# 3. Modelo Conceptual Extendido: Especialización y Generalización

## 3.1 Identificación de jerarquías

### Superclases y subclases identificadas

Dentro del modelo conceptual extendido se identificó una jerarquía correspondiente a la entidad **EMPLEADO**.

La superclase es:

- **EMPLEADO**

Las subclases identificadas son:

- **MOZO**
- **CAJERO**
- **COCINERO**

La especialización parte de la entidad **EMPLEADO**, definida como superclase, debido a que contiene los atributos comunes a todos los trabajadores del restaurante. A partir de esta superclase se identifican tres subclases: **MOZO**, **CAJERO** y **COCINERO**, las cuales representan funciones específicas dentro del sistema.

La estructura propuesta corresponde a una especialización **parcial** y **solapada**. Es parcial porque no todos los empleados necesariamente deben pertenecer a las subclases definidas. Es solapada porque un mismo empleado puede desempeñar más de una función dentro del restaurante.

### Herencia de atributos

Las subclases **MOZO**, **CAJERO** y **COCINERO** heredan todos los atributos definidos en la superclase **EMPLEADO**, por lo que no es necesario repetir dichos atributos en cada subclase. Los atributos heredados son los siguientes:

| Atributo | Clave | Descripción |
|---|---|---|
| id_empleado | PK | Identificador único del empleado. |
| dni | — | Documento nacional de identidad del empleado. |
| nombres | — | Nombres del empleado. |
| apellidos | — | Apellidos del empleado. |
| telefono | — | Teléfono de contacto del empleado. |
| correo | — | Correo electrónico del empleado. |

### Restricciones de la especialización

| Restricción | Valor | Interpretación |
|---|---|---|
| Completitud | PARCIAL | No todos los empleados deben pertenecer a alguna de las subclases definidas. |
| Disyunción | SOLAPADA | Un mismo empleado puede pertenecer a más de una subclase a la vez. |
